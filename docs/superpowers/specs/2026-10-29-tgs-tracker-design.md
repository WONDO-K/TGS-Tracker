# TGS Tracker — 고객사 요청·조치·배포 관리 시스템 설계서

작성일: 2026-10-29 · 버전: 1.3 · 상태: 구현용 설계 (GitHub Pages + Supabase, UX/UI 개선 반영)

## 1. 목적과 확정한 요구사항

고객사 요청을 내부 동료들이 함께 기록하고, 조치 내용과 테스트·운영 반영 여부를 확인한다. 특히 **테스트에 반영됐지만 운영에는 반영되지 않은 요청**을 즉시 찾을 수 있어야 한다.

- 고객사는 시스템에 로그인하지 않는다. 자료 전달은 이후 내보내기로 지원한다.
- 처음에는 고객사 한 곳을 사용하되, 여러 고객사를 등록할 수 있다.
- 한 사용자가 여러 고객사를 담당할 수 있다.
- 일반 사용자는 담당 고객사의 모든 요청을 조회·등록·수정한다. 작성자에 따라 접근을 제한하지 않는다.
- 관리자는 전체 고객사에 접근하고 고객사·사용자·담당 배정을 관리한다.
- 요청에 화면 캡처를 첨부한다. PC 공유 폴더 없이 웹에서 업로드한다.
- 진행 현황은 칸반으로 표시하고 테스트·운영 반영 여부는 별도로 관리한다.
- 기존 업무 기록은 사용자 접근 차단이나 고객사 사용 중지 후에도 보존한다.

배포는 사용자가 선택한 GitHub Pages + Supabase로 확정한다. 아직 사용자가 구체적으로 정하지 않은 화면 구성, 상세 필드, 파일 제한, 운영 규칙은 구현을 위한 기본값이다. 개발자가 새로 결정할 것은 시각 스타일, 작은 컴포넌트 분리, 오류 문구 등 이 요구사항을 바꾸지 않는 세부 구현이다.

## 2. 범위와 기술 선택

### 첫 버전에 포함

로그인·로그아웃·비밀번호 재설정, 초대 수락, 고객사별 접근 제어, 요청 등록·수정·상세, 칸반, 목록 보기, 검색·필터, 조치 기록, 이미지 첨부, 테스트·운영 반영 기록, 요청 보관·복원, 최소 관리자 화면.

### 이후 추가

고객사 전달용 XLSX 및 인쇄/PDF, 변경 알림, 통계, 세밀한 변경 이력, 배포 이력의 여러 회차 관리.

### 이번에 만들지 않음

고객사용 로그인, 공개 회원가입, 회사별 독립 가입·결제, 채팅, 업무 자동화, GitHub 커밋 자동 연동, 실제 서버 배포 실행 기능, 영상·일반 문서 첨부, 카드 순서 직접 저장.

여러 고객사 관리는 **하나의 내부 팀이 담당하는 고객사들을 구분하는 기능**이다. 여러 회사가 독립적으로 가입하는 SaaS 구조는 아니다.

### 검토한 접근

| 접근                                 | 장점                                      | 비용/판단                                           |
| ------------------------------------ | ----------------------------------------- | --------------------------------------------------- |
| React + Vite + TypeScript + Supabase | 별도 상시 서버 없이 업무 화면 구현에 집중 | 권장안. 기존 대화에서 제안한 구성을 기본값으로 채택 |
| Next.js + Supabase                   | 서버 렌더링과 서버 기능을 함께 확장       | 현재 요구에는 이점이 작고 학습 범위가 늘어남        |

Supabase는 Auth, PostgreSQL, Storage를 담당한다. 화면은 React Router와 일반 CSS로 구성하고, 칸반 이동에는 접근성을 지원하는 드래그 라이브러리를 사용한다. 드래그 없이 상태 선택으로도 동일한 작업을 할 수 있게 한다. Redux, 자체 API 서버, ORM, 범용 권한 엔진은 추가하지 않는다. 상세 패키지 버전은 구현 시 공식 호환 버전을 확인해 잠금 파일로 고정한다.

### 배포 구성 — GitHub Pages

- GitHub: 소스·SQL 마이그레이션·검증 코드 관리.
- GitHub Pages: GitHub Actions에서 `npm ci` → 타입 검사·검증 → `npm run build` → `dist` 업로드·배포. 저장소 Settings → Pages의 Source는 GitHub Actions로 지정한다.
- Supabase: DB·Auth·Storage 및 관리자 초대용 Edge Function.
- 프로젝트 사이트 `https://<owner>.github.io/<repo>/`는 Vite `base`를 `/<repo>/`로 설정한다. 계정 루트 사이트나 별도 도메인은 `/`를 사용한다. 실제 소유자·저장소 이름은 구현 시 확정하며 임의로 만들지 않는다.
- 라우팅은 HashRouter를 사용해 `/<repo>/#/board`, `/<repo>/#/requests/<id>` 형태로 제공한다. 서버의 SPA rewrite나 404 우회 파일에 의존하지 않는다. 아래 화면 경로들은 해시 안의 논리 경로다.
- GitHub Pages는 정적 프런트만 호스팅한다. DB·이미지·관리자 초대 함수는 Supabase에서 실행한다. Pages 접근 자체는 공개된 것으로 보고 업무 데이터는 Supabase 인증과 RLS로 보호한다.
- 소수의 내부 동료가 사용하는 시스템으로, 로그인 유무 때문에 별도 웹 서버나 다른 프런트 호스팅을 추가하지 않는다. 브라우저는 Supabase Auth에 직접 인증을 요청하고, 비밀번호·업무 데이터·첨부 이미지를 Pages 저장소나 정적 빌드에 저장하지 않는다.
- 기본 접근 제어는 활성 사용자 확인, 담당 고객사별 RLS, private 이미지 정책, 관리자 기능 검증으로 한정한다. 별도 SSO, 자체 인증 서버, 복잡한 권한 엔진은 첫 버전에 추가하지 않는다.
- GitHub 공식 문서의 민감한 거래 관련 이용 안내는 서비스 이용 시 참고할 외부 조건으로 기록한다. 이를 로그인 구현의 기술적 불가 사유나 호스팅 변경·추가 승인의 선행 조건으로 취급하지 않는다. 이 안내가 회사 내부 서비스에 대한 공식 사용 승인을 의미하는 것은 아니다.

## 3. 서비스 구조

```text
사용자 브라우저 — React
  ├─ Supabase Auth: 이메일·비밀번호 로그인
  ├─ Supabase Data API: RLS 검사 후 업무 데이터 조회·수정
  ├─ Supabase Storage: 고객사 권한 검사 후 이미지 업로드·다운로드
  └─ Supabase Edge Function: 관리자 검증 후 초대 이메일 발송

GitHub → GitHub Actions → GitHub Pages 정적 빌드 배포
```

일반 업무에는 별도 백엔드 서버가 없다. 다만 Auth 관리자 API로 초대하려면 비밀 키를 사용하는 서버 환경이 필요하므로 작은 Edge Function 하나를 둔다. 비밀 키는 브라우저에 배포하지 않는다.

## 4. 계정과 권한

### 계정 운영

1. 최초 관리자는 운영자가 Supabase에서 계정을 만들고, 보호된 SQL/콘솔 작업으로 관리자·활성 상태를 지정한다. 공개 API로 최초 관리자 승격을 제공하지 않는다.
2. 관리자가 이메일과 이름을 입력해 동료를 초대한다.
3. 초대받은 사용자는 비밀번호를 설정한다. 일반 가입 경로는 비활성화한다.
4. 관리자가 담당 고객사를 배정한다. 배정이 없으면 로그인은 가능하지만 업무 데이터는 보이지 않는다.
5. 접근 차단은 `profiles.is_active=false`로 처리한다. 이미 로그인한 세션도 이후 DB·Storage 요청에서 거부한다.
6. 계정을 삭제하지 않아 작성자 참조를 보존한다. 마지막 활성 관리자는 차단·강등할 수 없다.

### 권한표

| 동작                                      | 일반 사용자                       | 관리자                     |
| ----------------------------------------- | --------------------------------- | -------------------------- |
| 고객사·요청 조회                          | 담당 고객사만                     | 전체                       |
| 요청 등록·수정, 조치 추가, 배포 정보 수정 | 활성 담당 고객사만                | 활성 고객사 전체           |
| 이미지 조회·첨부                          | 요청 접근 범위와 동일             | 전체, 쓰기는 활성 고객사만 |
| 이미지 제거                               | 본인 첨부만, 활성·미보관 요청에서 | 활성·미보관 요청에서 전체  |
| 요청 보관·복원                            | 불가                              | 가능                       |
| 고객사·사용자·담당 배정 관리              | 불가                              | 가능                       |
| 자기 표시 이름 변경                       | 가능                              | 가능                       |
| 관리자 역할 부여·해제                     | 불가                              | 가능, 마지막 관리자 보호   |

사용 중지 고객사와 보관 요청은 읽기 전용이다. 사용 중지 고객사도 기존 담당자는 조회할 수 있으며 필터에서 명시적으로 선택한다. 담당 배정을 해제하면 해당 고객사에 대한 읽기 권한도 없어진다. 사용 중지 고객사의 요청을 다시 수정하려면 먼저 고객사를 활성화한다. 운영 반영 완료 요청도 활성·미보관 상태라면 메모 등 수정이 가능하다.

관리자 승격은 모든 고객사의 접근 권한을 부여하므로 확인 화면에 범위를 명시한다. 관리 기능의 서버·DB 검증을 통과해야 변경되며 UI 숨김에만 의존하지 않는다.

## 5. 진행 상태와 배포 규칙

### 칸반 상태

| 값           | 표시      | 의미                                  |
| ------------ | --------- | ------------------------------------- |
| received     | 접수      | 등록 후 작업 전                       |
| in_progress  | 진행 중   | 분석·개발·수정 중                     |
| verification | 확인 대기 | 조치 후 테스트 또는 확인 중           |
| completed    | 완료      | 조치·확인 완료. 운영 반영 여부와 별개 |

상태는 순차 이동을 강제하지 않고 되돌릴 수 있다. 보류 사유는 내부 메모로 남긴다. 완료는 운영 배포 완료를 뜻하지 않는다.

### 배포 정보

- `requires_deployment`: 배포 필요 여부, 기본 true.
- `test_deployed_at`, `production_deployed_at`: 실제 반영 시각, 미반영이면 null.
- DB에는 시간대를 포함하는 시각을 저장하고 화면은 한국 시간으로 표시한다.
- 배포 불필요로 변경하면 확인을 거쳐 두 반영일을 비운다. DB 제약으로 배포 불필요 상태의 반영일 저장을 막는다.
- 운영에 바로 반영한 예외를 기록할 수 있도록 테스트 반영을 운영 반영의 필수 조건으로 강제하지 않는다. 입력 시 안내만 표시한다.
- 반영일은 미래를 허용하지 않는다. 잘못 기록한 날짜는 수정·초기화할 수 있으며 변경 이벤트를 남긴다.
- 재작업·재배포가 필요한 건은 새 요청으로 등록하고 기존 요청 번호를 본문에 참조한다. 여러 배포 회차 추적은 이후 범위다.

**핵심 필터:** `requires_deployment=true AND test_deployed_at IS NOT NULL AND production_deployed_at IS NULL AND archived_at IS NULL`.

완료 열의 요청도 이 필터에 포함한다. 상단에는 같은 조건의 건수를 표시하며 현재 고객사·검색·기간 필터를 함께 반영한다.

## 6. 화면과 주요 동작

### 공통

- 데스크톱 업무 사용 우선, 좁은 화면에서는 목록으로도 작업 가능.
- 상단 탐색: 서비스명, 진행 현황·요청 목록, 관리자 메뉴, 계정. 모바일·태블릿에서는 메뉴를 접는다. 고객사 범위 선택은 검색 필터에 둔다.
- 운영 반영 대기 수를 테스트 → 운영 비교 요약으로 먼저 표시한다. 요약 선택으로 테스트 반영·운영 미반영 필터를 적용하며 네 개의 독립 KPI 타일은 사용하지 않는다.
- 모바일 요청 표는 고객사·요청일·상태·테스트/운영 정보를 유지한 목록으로 전환한다. 상세 복귀 시 원래 목록 경로와 필터를 유지한다.
- 상세의 운영 반영 요약은 모바일에서 긴 본문보다 먼저 표시한다. 상세 화면의 내부 메모·조치·이미지 저장 계약과 DB 권한은 기존 설계를 유지한다.
- 관리자에게만 고객사 관리·사용자 관리 메뉴를 표시한다.
- 로딩, 빈 목록, 권한 없음, 저장 실패를 서로 구분한다.
- 폼은 저장 성공 전 입력을 지우거나 창을 닫지 않는다.

### 로그인·계정 화면

`/#/login`, `/#/set-password`, `/#/reset-password`를 사용한다. 프로젝트 사이트에서는 저장소 경로가 앞에 붙는다.

Auth가 돌아올 실제 주소는 404가 나지 않는 배포 루트 `https://<owner>.github.io/<repo>/`로 설정한다. 인증 callback 처리를 HashRouter 시작 전에 수행해 인증용 URL 값과 화면 라우팅 해시가 충돌하지 않게 한다. PKCE code 또는 초대·복구 token_hash 등 실제 Auth 링크 형식에 맞춰 Supabase 공식 교환/검증 API를 사용한 뒤 URL의 인증 값을 지우고 비밀번호 설정 화면으로 이동한다. 인증 토큰을 HashRouter 경로로 해석하지 않는다. 초대 수락은 다른 기기에서도, 비밀번호 재설정은 만료·실패 상황에서도 검증한다.

로그인 후 접근 차단 여부를 검사한다. 담당 고객사가 없으면 “담당 고객사 배정이 필요합니다”를 표시한다. 초대 링크 만료 시 관리자에게 재발송을 요청하는 안내를 표시한다. 비밀번호 재설정과 초대는 등록한 서비스 URL로만 돌아온다.

### 진행 현황 `/board`

- 필터: 고객사, 제목·본문 검색, 요청일 범위, 작성자, 배포 상태.
- 배포 상태: 전체 / 테스트 미반영 / 테스트 반영·운영 미반영 / 운영 반영 / 배포 불필요.
- 기본값: 활성 고객사, 미보관 요청, 최근 수정 순. 검색은 300ms 지연 후 서버에서 실행한다.
- 카드: 요청 번호·제목·고객사·작성자·요청일·첨부 개수·테스트/운영 배지.
- 이미지 원본은 보드에서 내려받지 않는다.
- 상태 이동 시 DB 성공 후 최종 확정한다. 충돌·실패 시 이전 상태 유지와 오류 안내.
- 각 열은 30건부터 불러오고 “더 보기”로 추가한다. 합계는 현재 불러온 카드 수가 아니라 같은 필터의 DB 집계다.
- 별도 순서 필드 없이 각 열 내부는 최근 수정 순이다.

### 요청 목록 `/requests`

동일한 필터를 사용하고 번호·고객사·제목·진행 상태·테스트 반영일·운영 반영일을 표로 표시한다. 페이지당 30건. 관리자만 보관함을 선택할 수 있다. 이후 내보내기는 이 목록의 필터를 그대로 사용한다.

### 요청 등록·상세 `/requests/new`, `/requests/:id`

등록 필드: 고객사(필수), 제목(1~150자), 요청 내용(1~10,000자), 요청일(필수·기본 오늘), 요청자 이름(선택), 배포 필요 여부, 이미지(선택).

고객사를 하나만 담당하면 자동 선택한다. 여러 곳이면 선택해야 한다. 작성자는 로그인 사용자로 DB가 설정한다. 요청자 이름은 고객사의 실제 요청자를 기록하는 일반 텍스트이며 로그인 계정이 아니다.

상세 화면은 요청 내용·첨부, 진행/배포 정보, 고객사 전달용 조치 요약, 내부 활동 기록으로 구성한다. 고객사와 작성자는 생성 후 일반 수정으로 변경하지 않는다. 잘못된 고객사 등록은 관리자가 보관하고 올바른 고객사로 재등록한다.

조치 요약은 10,000자 이하로 현재 결과를 정리한다. 내부 활동은 “조치 기록/내부 메모” 유형으로 추가한다. 기존 활동은 수정·삭제하지 않고 정정 기록을 추가한다. 상태·배포·보관 변경은 시스템 이벤트로 자동 기록한다. 완전한 필드별 감사 로그는 첫 버전 범위가 아니다.

### 관리자 `/admin/customers`, `/admin/users`

- 고객사: 이름·코드·활성 상태. 이름/코드는 중복 불가. 사용 중지 시 새 요청과 기존 요청 수정을 차단한다.
- 사용자: 이름·이메일·역할·활성 상태·담당 고객사 목록. 이메일은 Auth와 일치시키고 앱에서 직접 수정하지 않는다.
- 사용자 초대·초대 재발송, 담당 고객사 다중 배정, 접근 차단, 역할 변경.
- 첫 버전에는 영구 삭제 버튼을 제공하지 않는다.

## 7. 데이터 모델

ID는 UUID, 요청 표시 번호는 DB identity bigint다. 생성/수정 시각은 `timestamptz`, 요청일은 `date`를 사용한다. 아래 표는 논리 스키마이며 구현 시 SQL 마이그레이션으로 제약·인덱스·권한까지 함께 작성한다.

| 테이블              | 주요 필드와 제약                                                                                                                                                                                                                                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| profiles            | id PK→auth.users, display_name, email, role(admin/member), is_active(default false), created_at. Auth 사용자 생성 트리거는 안전한 기본값(member/inactive)만 설정. 역할은 사용자 metadata에서 복사 금지                                                                                                                             |
| customers           | id, name unique, code unique, is_active(default true), created_at, updated_at                                                                                                                                                                                                                                                      |
| customer_members    | customer_id FK, user_id FK→profiles, created_at. 두 ID 복합 PK                                                                                                                                                                                                                                                                     |
| requests            | id, number unique identity, customer_id FK, title, description, requester_name nullable, requested_on, status, requires_deployment, test_deployed_at nullable, production_deployed_at nullable, action_summary(default ''), created_by FK, updated_by FK, created_at, updated_at, archived_at nullable, version integer(default 1) |
| request_activities  | id, request_id FK, kind(action/note/system), body, metadata jsonb, created_by FK, created_at. append-only                                                                                                                                                                                                                          |
| request_attachments | id, request_id FK, storage_path unique, original_name, mime_type, size_bytes, state(pending/ready), created_by FK, created_at                                                                                                                                                                                                      |

사용자·고객사·요청 참조에 연쇄 삭제를 설정하지 않는다. 일반 역할에 업무 데이터의 직접 삭제 권한을 부여하지 않는다.

`profiles.email`은 Auth 생성 시 DB에서 동기화하며 일반 사용자가 수정할 수 없다. 동료의 이름은 안전한 조회 함수로 같은 고객사 담당자 범위에서만 제공한다. 일반 사용자에게 전체 프로필과 이메일을 공개하지 않는다.

인덱스: requests(customer_id, archived_at, status, updated_at), requests(customer_id, requested_on), customer_members(user_id, customer_id), request_activities(request_id, created_at), request_attachments(request_id, state). 제목·본문의 한국어 검색은 처음에는 부분 일치로 구현한다. 검색 길이를 제한하고 SQL 문자열 연결 대신 매개변수를 사용한다. 핵심 필터의 부분 인덱스는 실제 조회 계획에 따라 추가한다.

## 8. DB·Storage 보호와 업데이트 API

### RLS 접근 정책

- 모든 공개 테이블에 RLS를 활성화한다. 미로그인 사용자에게 업무 데이터를 허용하지 않는다.
- `is_active_admin()`, `can_access_customer(customer_id)`는 DB의 현재 활성 상태와 담당 배정을 확인한다. 오래된 JWT의 역할 정보에 의존하지 않는다.
- 보조 함수는 RLS 재귀를 피하는 보호된 스키마에 두고 고정 search_path, 완전히 한정한 객체 이름, 최소 실행 권한을 사용한다.
- 읽기는 담당 범위 또는 관리자, 쓰기는 추가로 활성 고객사·미보관 요청인지 확인한다.
- 자신의 표시 이름만 수정할 수 있다. 일반 사용자는 role/is_active/email/id를 바꿀 수 없다.
- 작성자·수정자·시각·version은 DB가 설정해 클라이언트의 위조를 막는다.

### 쓰기 API

일반 역할의 직접 INSERT/UPDATE/DELETE를 제한하고 검증을 수행하는 소수의 DB 함수(RPC)로 업무 변경을 처리한다.

| 함수                                                 | 동작                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------ |
| create_request(payload)                              | 작성자를 설정하고 요청 ID 반환                                                 |
| update_request(id, expected_version, patch)          | 허용 필드만 변경. 버전 충돌 시 거절. 상태·배포 이벤트는 같은 트랜잭션에서 기록 |
| add_request_activity(request_id, kind, body)         | action/note 추가만 허용. system 위조 금지                                      |
| set_request_archived(id, expected_version, archived) | 관리자만 보관·복원 및 이벤트 기록                                              |
| save_customer(...)                                   | 관리자만 고객사 생성·수정                                                      |
| set_customer_members(user_id, customer_ids)          | 관리자만 담당 고객사 일괄 변경                                                 |
| set_user_access(...)                                 | 관리자만 역할·활성 상태 변경. 마지막 활성 관리자 보호                          |

SECURITY DEFINER 함수도 auth.uid(), 현재 활성 여부, 담당 범위를 매번 검사한다. 소유자 권한으로 RLS를 우회할 수 있으므로 함수 내부의 명시적 검증이 필수다. PUBLIC/anon 실행 권한은 제거하고 authenticated에 필요한 함수만 허용한다. 오류 메시지로 다른 고객사의 존재나 데이터를 노출하지 않는다.

마지막 활성 관리자 보호는 잠금이 있는 트랜잭션으로 구현해 동시 강등도 막는다. 같은 요청의 동시 수정은 version 비교로 감지하며, 충돌 시 입력을 보존하고 새로고침을 안내한다. 자동 병합은 구현하지 않는다.

## 9. 이미지 첨부

- 버킷 `request-images`는 private으로 설정한다.
- JPEG/PNG/WebP만 허용. SVG/GIF/동영상은 제외한다.
- 선택할 원본 최대 10MB, 저장 파일 최대 2MB, 요청당 최대 5장. 버킷에서도 저장 크기와 MIME을 제한한다.
- 브라우저에서 긴 변 1920px 이하로 줄이고 글자 가독성을 확인할 미리보기를 제공한다. 2MB 이하로 만들 수 없으면 안내하고 재선택하게 한다. 작은 PNG는 불필요하게 재압축하지 않는다.
- 경로는 `{customer_id}/{request_id}/{attachment_id}.{ext}`. 원본 이름은 경로에 쓰지 않는다.
- DB에는 Storage 경로를 저장한다. PC 경로나 만료되는 URL을 저장하지 않는다.
- 표시는 인증된 download → Blob URL 방식으로 하고 화면을 떠나면 해제한다. 영구 공개 URL은 만들지 않는다. 권한 해제 후 새 다운로드는 거부하지만 이미 열거나 저장한 파일까지 회수할 수는 없다.
- Storage SELECT/INSERT/DELETE도 담당·활성 상태를 검사한다. 경로뿐 아니라 요청과 첨부 행의 일치도 확인한다. UPDATE/upsert는 허용하지 않는다.

### 파일과 DB 불일치 처리

1. 먼저 요청 본문을 저장해 요청 ID를 얻는다.
2. `reserve_attachment`로 첨부 자리를 예약한다. 요청 행을 잠가 pending+ready 합계 최대 5장을 강제하고 UUID 경로를 생성한다.
3. pending 행과 일치하는 경로로 Storage에 업로드한다.
4. `finalize_attachment`에서 파일의 존재·크기·종류를 확인하고 ready로 변경한다. pending은 일반 첨부 목록에서 제외한다.
5. 실패 시 본문 저장 성공과 이미지 실패를 구분해 표시한다. 재시도할 수 있으며 취소 시 파일 삭제 성공 후 pending 행을 삭제한다.
6. ready 첨부 삭제도 Storage API로 실물을 먼저 삭제한 다음 DB 행을 삭제한다. 중간 실패는 재시도하며 이미 삭제된 같은 경로는 성공으로 취급한다.

Storage 메타데이터를 SQL DELETE로 지워 파일 삭제를 대신하지 않는다. 실물 삭제는 Storage API를 쓴다. 비정상 종료로 남은 pending은 재방문 시 재시도·취소할 수 있도록 한다. 운영 문서에 관리자용 잔여 pending 조회·파일 확인·정리 절차를 남긴다. DB와 Storage가 하나의 원자적 트랜잭션으로 동작한다고 가정하지 않는다.

한 장 500KB·요청당 3장이면 요청당 약 1.5MB다. 무료 1GB에 무제한으로 누적할 수는 없다. 실제 크기를 기록하고 Supabase 대시보드에서 사용량을 확인한다. 용량 부족 시 첨부만 실패로 처리하고 본문을 잃지 않는다.

## 10. 관리자 사용자 초대

Edge Function `invite-user`는 이메일 초대·재발송에 필요한 Auth Admin 작업에 한정한다.

1. Authorization 토큰을 검증해 요청자를 확인한다.
2. DB에서 현재도 활성 관리자인지 검사한다.
3. 이메일·이름을 검증하고 고정 또는 허용 목록의 callback URL로 inviteUserByEmail을 실행한다. 임의의 redirect 주소는 받지 않는다.
4. 초대 사용자 프로필을 member/active로 설정한다. 담당 고객사는 관리자가 별도로 배정한다. 기존 사용자 재발송이 역할과 배정을 초기화하면 안 된다.
5. Auth 생성과 DB 변경은 원자적이지 않다. 중간 실패 시 inactive로 남겨 접근을 막고 같은 이메일의 미완료 초대를 복구 가능하게 한다.
6. 기존 계정은 Auth가 지원하는 재발송·복구 흐름으로 처리한다. 이메일 중복 오류를 성공으로 표시하지 않는다. 재발송 간격을 제한한다.

운영 전 SMTP 발신자·수신자 제한·발송 한도를 확인하고, 설정된 환경에서 실제 동료 초대를 검증한다. 기본 이메일 설정만으로 임의의 동료에게 초대가 도착한다고 가정하지 않는다.

## 11. 후속 Excel·문서 출력

2차 버전에서 현재 목록 필터 결과를 XLSX로 출력한다. 화면에 로딩된 페이지만이 아니라 조건에 해당하는 전체 요청을 가져오되 RLS 범위를 넘지 않는다.

출력 열: 요청 번호, 고객사, 요청일, 제목, 요청 내용, 고객사 전달용 조치 요약, 진행 상태, 테스트 반영일, 운영 반영일.

내부 메모·직원 이메일·이미지 링크는 기본 출력에서 제외한다. 내부 조치 기록을 그대로 내보내지 않고 action_summary를 사용한다. 문자열이 수식으로 실행되지 않도록 출력한다. PDF/문서는 인쇄 전용 화면을 추가한 뒤 지원한다. 첫 버전에 Word 생성 기반을 만들지 않는다.

## 12. 파일 구성과 구현 순서

```text
src/
  app/               HashRouter·인증 callback 선처리·로그인 상태·공통 레이아웃
  features/auth/     로그인·초대 수락·비밀번호 재설정
  features/requests/ 보드·목록·상세·등록·첨부
  features/admin/    고객사·사용자 관리
  components/        작은 공통 UI
  lib/               Supabase 연결·날짜·오류 처리
supabase/
  migrations/        테이블·제약·함수·RLS·Storage 설정
  functions/invite-user/
  tests/             권한·변경 정합성 검증
.github/workflows/
  deploy-pages.yml   검증·정적 빌드·Pages 배포
```

1. React/Vite/TypeScript, 라우팅, 로그인 화면, 환경변수 예시를 준비한다.
2. 마이그레이션으로 스키마·RLS·RPC를 만들고 고객사 2곳, 관리자, 중복 담당자, 비담당자 데이터로 접근 분리를 먼저 검증한다.
3. 최초 관리자 설정, 초대, 고객사 등록, 담당 배정, 접근 차단을 구현한다.
4. 요청 등록 → 상세 → 수정 → 조치 기록 → 배포 정보의 전체 흐름을 완성한다.
5. 고객사별 목록·검색·배포 필터와 건수를 구현한 다음 칸반과 상태 이동을 추가한다.
6. private 이미지 예약·업로드·표시·삭제·실패 복구를 구현한다.
7. 저장 충돌, 보관·복원, 좁은 화면과 키보드 조작을 확인한다.
8. 타입 검사·빌드·권한 검증·대표 흐름 확인 후 GitHub Actions와 Pages를 연결한다. 배포 job에 pages:write 및 id-token:write 등 필요한 최소 권한과 github-pages environment를 설정한다.
9. 가상 데이터 데모와 README에 현장 문제·설계 판단·역할별 동작·화면·설치 및 운영 절차를 남긴다.

## 13. 완료 기준

- 관리자가 고객사 2곳과 사용자를 설정하고 한 사용자에게 여러 고객사를 배정할 수 있다.
- 같은 고객사 담당자끼리는 서로 작성한 요청을 열고 조치 기록·상태를 변경할 수 있다.
- 비담당 고객사 데이터는 URL 직접 입력, Data API/RPC 직접 호출, 이미지 다운로드로도 조회·수정할 수 없다.
- 일반 사용자는 관리자 승격이나 담당 배정을 위조할 수 없다.
- 차단된 사용자는 기존 로그인 세션으로도 새로운 데이터·이미지를 받을 수 없다.
- 동시 작업으로 마지막 활성 관리자가 사라지지 않는다.
- 완료 열을 포함해 테스트 반영·운영 미반영 목록이 누락 없이 나오며 건수가 일치한다.
- 두 사용자의 동시 수정은 충돌로 감지하고 조용히 덮어쓰지 않는다.
- 상태·배포 변경과 시스템 이벤트가 함께 저장되며 작성자·수정자를 위조할 수 없다.
- 이미지 실패에도 본문이 남고, 직접 API 호출에서도 첨부 수·크기·MIME 제한을 지킨다.
- 다른 고객사 경로 위조·첨부 예약 수 초과·권한 없는 첨부 삭제가 거절된다.
- 고객사 사용 중지와 요청 보관 시 읽기 전용이 되며 재활성화·복원 후 수정할 수 있다.
- GitHub Pages의 저장소 하위 경로에서 정적 파일이 로드되고, 해시 상세 주소 직접 접속·새로고침과 인증 callback이 정상 동작한다.

## 14. 설정·운영·포트폴리오

- 브라우저에는 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`만 둔다. VITE 환경변수는 공개되는 값이다.
- secret/service_role 키, DB 비밀번호, SMTP 인증정보는 서버 측 secret으로만 보관한다. GitHub나 프런트 환경변수에 넣지 않는다.
- Auth Site URL과 허용 redirect에 localhost와 정확한 Pages 배포 루트(저장소 하위 경로 포함)를 등록한다. HashRouter의 화면 주소를 Auth callback 주소로 사용하지 않는다. 미리보기 배포가 자동으로 실무 DB에 연결되지 않게 한다.
- 공개 포트폴리오는 정적 가상 데이터로 동작하는 별도 데모 빌드로 제공한다. `VITE_APP_MODE=demo`에서는 Supabase 클라이언트와 로그인 흐름을 시작하지 않고 저장소의 가상 데이터만 표시한다. 실무 빌드에서 사용할 수 있는 인증 우회 모드를 만들지 않는다.
- 데모는 보드·목록·상세 조회만 제공하며 편집·관리·초대 발송 기능은 제거한다. 실무와 별도의 배포 주소를 사용하고 Supabase 연결 환경변수도 주입하지 않는다. 편집과 관리자 흐름은 가상 환경 영상으로 소개한다. 별도 데모 DB나 새 읽기 전용 사용자 역할은 첫 버전에 추가하지 않는다.
- 실제 고객사명·요청·이미지는 저장소, seed, 공개 데모에 넣지 않는다.
- DB와 이미지는 별도로 백업하고 복원 절차를 기록한다. 무료 플랜의 중지·보관·백업 조건을 운영 시작 시 확인하고 업무 기록 보존 방침을 정한다.
